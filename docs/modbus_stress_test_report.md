## 第二部分: 极限测试

### 8. 异步泛洪测试

#### 8.1 测试方法

使用原始串口 (raw serial) 绕过 pymodbus 同步等待, 连续发送多帧 Modbus FC03 请求后不等响应, 统计设备实际处理能力。

| 参数 | 值 |
|------|-----|
| 泛洪帧数 | 3, 5, 10, 20, 50 |
| 帧间延迟 | 0us, 500us, 1000us |
| 每组轮次 | 3 |
| 请求帧 | FC03 读 2/4 寄存器, 交替地址 0/20/40/60 |

#### 8.2 测试结果

| 轮次 | 泛洪量 | 帧间隔 | 发送耗时 | 正确响应 | 异常响应 | 丢失 | 设备状态 |
|------|--------|--------|---------|---------|---------|------|---------|
| 1 | 3 帧 | 0us | 0.9ms | 0 | 0 | 3 | 存活 |
| 2 | 3 帧 | 0us | 0.9ms | 0 | 0 | 3 | 存活 |
| 3 | 3 帧 | 0us | 0.9ms | 0 | 0 | 3 | 存活 |
| 4 | 3 帧 | 500us | 2.9ms | 0 | 0 | 3 | **崩溃** |

**总发送: 12 帧, 成功: 0, 设备崩溃于第 4 轮。**

#### 8.3 崩溃分析

**0us 间隔 (帧合并为单字节流):**
- 3 帧 FC03 请求 (~24 字节) 在 0.9ms 内连续发出
- 设备 DMA 接收完整字节流, 但 IDLE 中断未触发 (无帧间静默)
- 设备无法拆分帧, 全部丢弃, 但 DMA 缓冲区溢出后自行恢复
- 设备存活 3 轮后仍未崩溃

**500us 间隔 (帧间有微小间隔):**
- 3 帧在 2.9ms 内发出, 帧间 ~500us 间隔
- 500us 间隔足以触发 IDLE 中断 (Modbus 规范 3.5 字符时间 ≈ 0.3ms @115200)
- 设备开始尝试处理第一帧, 发送响应时 DE=HIGH 阻断后续帧接收
- 第二帧到达时设备正在发送第一帧响应 → DMA 缓冲区与 IDLE 中断冲突
- 设备主循环卡死, 看门狗未及时喂狗, **设备崩溃且无法自动恢复**

#### 8.4 崩溃后验证

设备崩溃后, 使用 pymodbus 同步客户端进行 16 项边界地址测试, **全部超时 (2s timeout)**, 确认设备完全无响应, 需硬件复位恢复。

#### 9.2 边界测试结论

**通过: 7/16, 未达预期: 9/16**

设备 Modbus 处理器存在以下问题:

1. **不校验寄存器地址越界** — 地址 124~65535 均返回 OK 而非 Modbus 异常码 02 (Illegal Data Address)。设备直接读取内存中对应偏移位置的数据, 存在信息泄露风险。

2. **不校验读取长度越界** — 请求读取 124~125 个寄存器时, 实际读取范围超出定义的寄存器空间 (0~123), 但仍返回 OK。

3. **长度为 0 时无响应** — count=0 的请求导致设备超时无响应, 未返回异常码 03 (Illegal Data Value)。

4. **大范围读取正常** — 地址 0 读取 123 个寄存器 (覆盖全部有效空间) 可正常完成, 延迟约 17ms。

## 第三部分: 综合结论

### 10. 同步抗压结论

设备在标准 Modbus 通信模式 (主站发送→等待响应→发送下一帧) 下表现极为稳定:

- **33,530 次同步请求 100% 成功**, 零超时、零异常、零 CRC 错误
- 即使 **0ms 帧间隔连续请求 15,530 次** (同步模式), 设备仍能正确响应
- 响应延迟稳定: 单寄存器 ~5.6ms, 10 寄存器 ~7.3ms, 最大约 20ms
- 不同寄存器地址区间 (0~90) 表现一致
- **吞吐量: ~159 次/秒**, 满足工业采集需求

### 11. 异步泛洪结论 (已知风险)

| 场景 | 结果 | 严重性 |
|------|------|--------|
| 标准同步通信 (等响应再发) | 33,530 次 100% 成功 | — |
| 3 帧无间隔泛洪 (0us) | 0 响应, 设备存活 | 中 |
| 3 帧微间隔泛洪 (500us) | 0 响应, **设备崩溃** | **严重** |

**设备在异步泛洪场景下存在崩溃风险。** 根因分析:

1. RS-485 半双工 DE 引脚控制 — 响应期间 DE=HIGH 阻断接收
2. IDLE 中断与 DMA 缓冲区竞争 — 帧间隔足够触发 IDLE 但来不及处理
3. 主循环阻塞 — 处理异常帧时可能长时间未喂看门狗

**实际风险评估:** 标准工业 Modbus 主站均采用同步模式 (发一帧等一帧), 此崩溃场景在实际应用中不会发生。仅当非标设备或恶意攻击者进行泛洪时才会触发。

### 12. 边界校验结论

设备 Modbus 处理器不校验寄存器地址和读取长度的合法性:

| 问题 | 影响 | 建议 |
|------|------|------|
| 越界地址返回 OK 而非异常码 | 不符 Modbus 规范; 暴露内存数据 | 增加 `if (addr + count > 124) return EXCEPTION_ADDR` |
| count=0 无响应 | 主站超时等待 | 增加 `if (count == 0) return EXCEPTION_VALUE` |
| 大范围读取正常 | 无负面影响 | 可作为快速批量读取手段 |

### 13. 改进建议

**优先级 高 — 异步泛洪崩溃防护:**

1. 在 `UartReceive_IDLE()` 中增加帧长度合法性检查, 异常帧直接丢弃不复位 DMA
2. 主循环中 `Uart2_Communication()` 增加超时保护, 防止单帧处理阻塞过久
3. 考虑在 TIM3 10ms 中断中增加通信计数器, 异常高频时自动复位 UART 外设

**优先级 中 — 边界地址校验:**

4. `Modbus_Function_3()` 入口增加地址范围检查: `addr + count > 124` 返回异常码 02
5. `count == 0` 返回异常码 03

**优先级 低 — 防御性增强:**

6. DMA 缓冲区增加溢出检测, 超过 `UART_RX_LEN` 时丢弃当前帧
7. 考虑增加连续错误帧计数器, 超过阈值时软复位 UART2 外设
